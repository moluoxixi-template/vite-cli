# 面试口播稿：Vite CLI 脚手架项目

## 开场（30 秒）
大家好，我这个项目是一个前端脚手架 CLI，包名是 `@moluoxixi/create-app`，核心目标是把“新项目初始化”标准化。  
它不是简单复制模板，而是基于配置做分层叠加，自动生成一个可运行、可检查、可扩展的 Vue/React 项目骨架，并按选择注入路由、状态管理、国际化、Sentry、代码规范和微前端能力。

## 一句话讲清架构（15 秒）
整体是五层：`命令入口层 -> 交互配置层 -> 项目生成层 -> 模板渲染/Feature 叠加层 -> 安装与初始化层`。  
主线函数是：`createProject -> collectProjectConfig -> generateProject -> renderTemplate/renderFeatures -> installDependencies/initGit`。

## 项目整体架构（1-2 分钟）
如果我按代码目录讲，会是这五块：

1. `src/index.ts` + `src/commands/create.ts`  
负责 CLI 生命周期，接收命令、展示进度、组织主流程和异常处理。

2. `src/core/prompts.ts`  
负责收集用户配置，包含输入校验、默认值策略（比如从 npm/git 配置推断作者信息）、以及配置归一化。  
例如路由模式会被转换成布尔 Feature（`manualRoutes` / `pageRoutes`），状态管理会按框架自动映射为 `pinia` 或 `zustand`。

3. `src/generators/project.ts`  
负责“编排”，不是做细节。它定义了核心执行顺序：  
先清空目录，再按 `L1 common/base -> L2 framework/base -> L3 micro-frontend/base` 渲染基础模板，然后叠加 features，最后修正 `package.json` 元数据与包管理器文件。

4. `src/core/template.ts` + `src/core/feature.ts`  
这是最关键的能力层。  
`template.ts` 处理文件复制、`package.json` 深度合并、特殊文件重命名（`_gitignore -> .gitignore`）等。  
`feature.ts` 通过扫描文件系统自动发现 feature 目录，不依赖硬编码列表，按配置动态渲染。

5. `src/utils/*`  
放纯工具能力，比如路径安全校验、深度合并、依赖排序、依赖安装重试、Git 初始化。  
这样核心业务和工具职责隔离，后续维护成本更低。

## 设计思想（1-2 分钟）
我会重点强调四个设计思想：

1. 分层叠加而不是单模板分叉  
通过三层模板覆盖机制解决“共性 + 框架差异 + 架构差异”共存问题，避免模板数量爆炸。

2. 约定优于配置，配置驱动生成  
Feature 的配置键和目录名保持一致，做到“加目录即加能力”，降低接入新功能成本。

3. 结构化合并而不是粗暴覆盖  
`package.json` 使用深度合并 + 依赖排序，保证多层模板叠加后仍然可读、可控、稳定。

4. 可测试性优先  
测试不是补充，而是设计前置。单测验证核心函数，E2E 验证真实生成流程和依赖行为，确保脚手架输出可以直接落地。

## 关键注意点（面试加分项）
这部分我通常会主动讲，体现工程思维：

1. 覆盖顺序是系统行为的核心  
必须明确后渲染覆盖先渲染，否则 feature 和微前端覆盖关系会错乱。

2. Feature 命名强约束  
配置键与目录名绑定，规范统一带来扩展效率，但也要求命名治理和文档同步。

3. 路径与文件安全  
模板渲染中做了路径校验，避免 `..` 等路径穿越风险；同时跳过 `node_modules`、`.ejs` 等非目标内容。

4. 安装与初始化要“可失败但不中断核心价值”  
项目生成成功是主目标；Git 初始化和依赖安装失败会给出可恢复提示，避免用户全流程失败。

5. 当前版本能力边界要诚实说明  
代码里保留了 React 与更多 UI 库模板，但交互选项当前聚焦 Vue 线路，这是受模板成熟度约束的阶段性策略。

## 质量保障与测试策略（1 分钟）
测试采用独立 workspace（`__test__`）管理，分三层：

1. 单元测试：验证 `deepMerge`、`sortDependencies`、feature 映射等纯逻辑。
2. 结构与导入校验：扫描模板，检查是否存在跨模板导入、依赖声明缺失等问题。
3. E2E：按功能组合生成真实项目，执行安装、类型检查、lint、依赖验证，确保输出可运行。

这套策略的价值是：不仅验证“代码是否正确”，还验证“脚手架产物是否可靠”。

## 结尾（20 秒）
总结一下，这个项目本质上是在做“工程标准化产品”：  
通过分层模板、Feature 自动发现和可测试编排，把复杂项目初始化流程沉淀成可复用能力。  
我在这个项目里重点关注的是扩展性、可维护性和交付稳定性，而不只是“能生成项目”。

## 可能被追问时的短答模板
1. 为什么要三层模板？  
为了把公共能力、框架差异和微前端差异拆开，减少模板分叉和重复维护。

2. 怎么保证新 Feature 不破坏旧项目？  
通过目录扫描 + 配置开关 + E2E 组合测试，新增能力默认可插拔，不影响未开启场景。

3. 你觉得当前最大风险是什么？  
覆盖顺序和命名约定是隐式契约，必须靠文档、校验和测试共同兜底。
