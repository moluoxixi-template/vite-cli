# 前端从0到1面试故事（医疗行业版本）

> 说明：以下案例基于真实项目经验做了脱敏与合理虚构，数据为可自洽口径，适合大厂前端/前端架构岗位面试表达。

## 个人角色与项目底座（统一设定）
- 角色：前端核心开发，后期承担前端小组技术负责人职责（5年经验）
- 项目：区域医疗云平台从0到1，覆盖互联网问诊、电子处方、检查报告、电子病历、医院管理后台
- 覆盖范围：12家医院，医生端 + 护士端 + 运营管理端 + 医疗设备终端（老旧浏览器）
- 前端技术：Vue 3 + TypeScript + Vite/Webpack + Pinia/Vuex + Axios + Vue Router + 微前端 + Jest + Cypress + Jenkins/GitLab CI
- 目标：在合规前提下提升性能、稳定性、交付效率，并支撑多团队并行开发

## 场景1：高并发下首屏慢与运行时卡顿（问诊工作台）

### 1) 业务背景与目标
问诊工作台是医生日常最高频页面，集成患者队列、病历表单、检查报告、历史处方四个区域。系统上线初期每天高峰同时在线约3200名医生。目标是把首屏可用时间控制在3秒内，医生录入时不能明显卡顿（INP < 200ms）。

### 2) 初始方案
初版采用 Vue 3 + Vite + Pinia，页面单路由承载全部模块；为了开发效率，病历主表单和附属表单都挂在同一个响应式对象上，通过深度 `watch` 做自动保存。列表区使用普通表格组件，无虚拟滚动。

### 3) 踩坑表现
- 医生反馈“打开病人详情要等半天”，尤其早高峰更明显。
- 首屏 LCP 6.4s，INP 420ms，低配终端输入时出现明显掉帧。
- 病历页切换患者时偶发 2~3 秒冻结，导致误以为系统无响应。

### 4) 排查过程
- 用 Web Vitals + Sentry Performance 做分医院/分机型拆解，确认问题集中在病历详情页。
- Chrome Performance 录制发现主线程被大量 JSON 序列化、深层依赖追踪占满。
- Vue DevTools 定位到多个深度 `watch` 在同一输入动作下被重复触发。
- Network Waterfall 看到 11 个串行接口，且报告数据与病历数据重复拉取。

### 5) 根因分析
技术根因：
- 单页承载过重，首屏加载了太多非关键模块。
- 大表格未虚拟化，DOM 节点数过高。
- 深度 `watch` + 自动保存策略导致频繁全量 diff。
- 接口编排是串行，且缺少缓存层。

流程根因：
- 0到1阶段只看功能闭环，缺少明确性能预算。
- 联调时用的是测试小数据，未模拟真实医院高负载数据量。

### 6) 解决方案
短期止血：
- 先关掉“每次输入即自动保存”，改为 800ms 防抖 + 显式保存按钮兜底。
- 对非首屏模块改成懒加载，优先保证患者信息与核心病历可交互。
- 把串行接口改为并行请求，失败模块不阻断主流程。

长期治理：
- 病历工作台做“壳 + 业务子模块”拆分，关键路径最小化。
- 引入虚拟列表（患者队列、历史处方）并做行级 memo。
- 表单状态拆为“编辑态局部 store + 提交态聚合 store”，避免全量响应式联动。
- 建立性能预算（LCP、INP、JS 体积）并接入 CI 门禁。

### 7) 架构取舍
备选方案A：上 SSR（Nuxt）提升首屏。
- 优点：理论首屏更快。
- 缺点：医院内网 + 强登录态 + 大量实时交互，SSR收益有限，改造成本高。

备选方案B：继续 CSR，但做关键路径瘦身 + 运行时优化。
- 优点：兼容现有体系，见效快，风险低。
- 缺点：需要较强工程治理，不是一招见效。

备选方案C：重写为 Canvas 表格渲染。
- 优点：极端数据量下性能好。
- 缺点：可维护性和可访问性差，表单生态适配成本高。

最终决策：选 B。先把关键路径和状态联动问题解决，再局部引入虚拟化，ROI最高。

### 8) 结果量化
- LCP：6.4s -> 2.7s
- INP：420ms -> 155ms
- 首屏 JS 体积：3.8MB -> 2.1MB
- 病历页卡顿投诉工单：周均 38 -> 9（下降约76%）

### 9) 复盘沉淀
- 沉淀《前端性能预算规范》：按页面定义首屏预算与交互预算。
- 建立“性能压测样本库”：脱敏后的大病历/大报告数据用于回归。
- 发布前强制跑性能冒烟，超阈值禁止合并。

### 10) 面试表达版本
#### 30秒电梯版
我在医疗问诊工作台从0到1上线时踩过一个大坑：页面把病历、报告、处方全塞进一个路由，深度 watch 又做自动保存，导致高峰期 LCP 超6秒、输入卡顿。后来我先做止血，关闭实时全量保存并改并行请求；再做长期治理，拆关键路径、虚拟列表、重构状态模型并加性能门禁。最终 LCP 降到 2.7 秒，INP 降到 155ms，医生侧卡顿投诉下降 76%。

#### 3分钟完整版（STAR）
- S（场景）：区域医疗平台上线后，医生问诊工作台在高峰时段严重卡顿，直接影响接诊效率。
- T（任务）：我负责在不延期业务上线的情况下，把首屏和输入体验拉回可用区间，并建立可持续性能治理。
- A（行动）：先用 Sentry + Web Vitals 分层定位，确认主因是深度 watch、非关键模块首屏加载、串行接口和大表格未虚拟化。短期先止血：自动保存防抖化、并行请求、懒加载非关键模块。长期做架构治理：壳层拆分、状态分层、虚拟列表、CI 性能门禁。
- R（结果）：LCP 从 6.4s 降到 2.7s，INP 从 420ms 降到 155ms，工单大幅下降，并且后续版本性能波动明显收敛。

#### 面试官可能追问3个问题 + 最佳回答
1. Q：为什么不用 SSR 一步到位？
   A：我们是强登录态内网系统，首屏后交互比首屏渲染更关键，SSR带来的链路复杂度和部署成本高于收益，所以先做 CSR 关键路径优化，性价比更高。
2. Q：Vue 3 下你怎么避免响应式过度触发？
   A：我把全局深对象拆成局部 store，减少深层 watch；高频输入用浅层状态和节流更新，提交时再聚合，避免每次输入触发全量联动。
3. Q：怎么防止回归后再次变慢？
   A：把 LCP/INP/包体积写进 CI 门禁，PR 阶段即拦截；同时用固定脱敏样本做性能回归，保证指标可比。

### 可背诵话术
这个场景我最想强调的是，我一开始也犯了“功能先跑通、性能后补”的典型错误。后来我把问题拆成两层：先止血保证医生能用，再把性能预算和CI门禁制度化。面试里我会突出这点：我不只会调几个参数，而是把性能问题转成可持续治理能力。

## 场景2：数据一致性与状态管理失控（病历与处方联动）

### 1) 业务背景与目标
电子病历与电子处方需要强一致：诊断、过敏史、剂量、频次必须同步。目标是把“提交成功但数据不一致”的比例降到千分之一以内，同时支持医生多标签页并行操作。

### 2) 初始方案
早期是 Vuex 模块 + 局部组件状态混用，后续迁到 Pinia 时采用“模块逐步迁移”。为了提速开发，不同业务组各自维护 store，病历和处方通过事件总线同步。

### 3) 踩坑表现
- 医生先改诊断再改处方，偶发提交后剂量回滚到旧值。
- 多标签页编辑同一患者时，后保存覆盖先保存。
- 联调阶段出现“前端显示成功，后端落库失败”的错觉。

### 4) 排查过程
- 给每次保存增加 `requestId + patientId + version` 追踪，串起前端日志和后端链路。
- 用 Pinia 插件记录 action timeline，重放冲突场景。
- 抓包发现同一字段在 1 秒内被两次不同版本请求覆盖。
- 对比数据库审计日志，确认存在并发写入覆盖而非纯展示问题。

### 5) 根因分析
技术根因：
- 单一事实源缺失：Vuex、Pinia、组件本地状态并存。
- 没有版本控制和幂等键，后到请求覆盖先到请求。
- 事件总线同步是“最终一致”，但缺乏冲突策略。

流程根因：
- 迁移期缺少统一状态建模规范。
- 联调关注接口通不通，未覆盖并发编辑场景。

### 6) 解决方案
短期止血：
- 提交期间加患者级写锁，禁止重复提交。
- 同一患者多标签页编辑给出冲突提示并限制提交。
- 提交失败改为强提示，禁止“静默失败”。

长期治理：
- 建立 Pinia 领域模型：`patientDomainStore` 作为唯一事实源。
- 写接口引入版本号（`If-Match`/`version`）+ 幂等键。
- 将“自动同步”改为“命令队列 + 可回放日志”，冲突时显式合并。
- 制定状态分层规范：UI态、领域态、提交态分离。

### 7) 架构取舍
备选方案A：继续 Vuex，严格模块边界。
- 优点：低迁移成本。
- 缺点：类型体验差，迁移期两套范式并存更复杂。

备选方案B：全面迁到 Pinia + 领域化单一事实源。
- 优点：TS 友好、组合式 API 更清晰，便于统一建模。
- 缺点：短期重构成本高。

备选方案C：引入 RxJS 做状态流。
- 优点：并发与流式能力强。
- 缺点：团队学习成本高，医疗项目交付节奏不允许大幅换心智。

最终决策：选 B，并保留 Vuex 兼容层 2 个迭代，平滑迁移。

### 8) 结果量化
- 提交后数据不一致率：2.3% -> 0.18%
- 并发覆盖问题：周均 27 单 -> 2 单
- 病历/处方联调返工时长：平均 3.5 天 -> 1.2 天

### 9) 复盘沉淀
- 输出《状态管理分层规范》与《冲突处理SOP》。
- 增加“并发编辑回归用例包”，纳入 Cypress 回归。
- 推出“保存链路可观测看板”，前后端共享同一口径。

### 10) 面试表达版本
#### 30秒电梯版
我在病历和处方联调里踩过一致性大坑：状态来源分散，迁移期 Vuex 和 Pinia 混用，导致并发覆盖和提交后回滚。我的处理是先加写锁和冲突提示止血，再重构成 Pinia 领域单一事实源，并引入版本控制和幂等键。最终数据不一致率从 2.3% 降到 0.18%。

#### 3分钟完整版（STAR）
- S：电子病历与处方联动场景出现“展示成功但实际不一致”，医生反馈强烈。
- T：我要在不停机迭代下，把一致性风险压到可控范围，并给跨团队一套统一状态范式。
- A：先通过 requestId + version 拉通前后端链路，定位并发覆盖；短期上写锁与冲突提示。随后做体系化改造：Pinia 领域化单一事实源、版本校验、幂等键、命令队列与冲突合并策略。
- R：一致性问题显著下降，联调返工时长减少，团队状态模型统一，后续需求接入速度更快。

#### 面试官可能追问3个问题 + 最佳回答
1. Q：为什么不用纯后端事务保证一致性？
   A：后端事务保证落库一致，但前端仍会有并发编辑与覆盖提交问题，前后都要做。前端必须有版本感知和冲突提示。
2. Q：Pinia 相比 Vuex，你最看重什么？
   A：类型推断和组合式组织能力，能把领域模型收敛到一个事实源，减少跨模块隐式依赖。
3. Q：冲突时为什么不自动覆盖最新？
   A：医疗场景有合规风险，自动覆盖可能吞掉关键诊疗信息。我们选择显式提示并让医生确认。

### 可背诵话术
我在这个问题上的成长是：状态管理不只是“库选型”，本质是数据治理。以前我只关注 store 怎么写，后来我更关注事实源、版本、幂等和冲突策略，这套方法在医疗场景尤其关键。

## 场景3：线上白屏与崩溃治理（含老旧医疗终端兼容）

### 1) 业务背景与目标
系统除了PC浏览器，还要跑在医院自助机和部分老旧终端。上线后目标是 Crash-Free Session > 99.5%，白屏率 < 0.1%。

### 2) 初始方案
新模块使用 Vite 默认现代构建，微前端子应用按需加载；监控只接了基础 Sentry 错误上报，未做 UA 分层。

### 3) 踩坑表现
- 某次发布后白屏率从 0.09% 飙到 1.3%。
- 主要集中在检验科老终端，报错“Unexpected token ?”。
- 少量用户遇到子应用加载失败后页面无限转圈。

### 4) 排查过程
- Sentry 按 release + UA + 医院维度聚合，迅速缩小到老旧 Chromium 终端。
- 通过远程调试和日志回放，定位到可选链与动态 import 语法兼容问题。
- 分析网关日志发现子应用静态资源有缓存错配，出现 404 与主应用版本不一致。
- 复盘发布记录，确认灰度阶段样本未覆盖老终端机型。

### 5) 根因分析
技术根因：
- 构建目标过新，缺少 legacy 兼容与必要 polyfill。
- 微前端主子应用版本协同机制薄弱，缓存策略不一致导致资源错配。
- 子应用加载失败没有降级视图与熔断处理。

流程根因：
- 灰度发布人群没有按设备类型分层。
- 监控看板缺少“终端机型维度”的核心指标。

### 6) 解决方案
短期止血：
- 立即回滚到上一个稳定版本并清理 CDN 缓存。
- 对加载失败子应用给兜底页面，避免整页白屏。

长期治理：
- 引入 `@vitejs/plugin-legacy`，明确浏览器兼容矩阵。
- 建立主子应用版本握手机制（版本清单 + 校验失败回退）。
- 统一缓存策略：入口 `no-cache`，静态资源 `immutable + hash`。
- 增加白屏探针、首屏心跳、设备维度告警。

### 7) 架构取舍
备选方案A：要求医院全面升级终端。
- 优点：技术栈最干净。
- 缺点：推进周期长，不可控，业务不能等。

备选方案B：保留现代构建，同时增加 legacy 兼容和运行时降级。
- 优点：兼顾演进和存量设备。
- 缺点：包体积略增，构建复杂度上升。

备选方案C：统一降到 ES2015 甚至更低。
- 优点：兼容最稳。
- 缺点：牺牲新设备性能，整体体验倒退。

最终决策：选 B，并推动设备升级作为中长期计划。

### 8) 结果量化
- 白屏率：1.3% -> 0.06%
- Crash-Free Session：97.8% -> 99.72%
- 子应用加载失败恢复成功率：34% -> 93%

### 9) 复盘沉淀
- 形成《医疗终端兼容基线》与《白屏应急预案》。
- 灰度策略改为“三维分层”：医院、科室、终端机型。
- 发布看板新增“白屏率/崩溃率/子应用加载成功率”三指标联动。

### 10) 面试表达版本
#### 30秒电梯版
我处理过一次典型线上事故：发布后老旧医疗终端白屏率从 0.09% 飙到 1.3%。排查发现是构建目标过新和微前端缓存错配叠加。短期我先回滚并加加载失败兜底，长期引入 legacy 构建、主子应用版本握手和缓存治理。最终白屏率降到 0.06%，崩溃率也回到稳定区间。

#### 3分钟完整版（STAR）
- S：一次版本发布导致检验科老终端大面积白屏，影响业务连续性。
- T：我需要在最短时间恢复可用，并建立防复发机制。
- A：先通过 Sentry 的 release+UA 维度锁定机型，再结合网关日志确认兼容与缓存双问题。应急回滚后，补了子应用降级页面。随后做系统治理：legacy 构建、版本握手、缓存统一策略、设备分层灰度与告警。
- R：白屏和崩溃指标全面恢复且优于事故前，后续类似问题没有再出现。

#### 面试官可能追问3个问题 + 最佳回答
1. Q：微前端白屏时为什么会拖垮主应用？
   A：早期把子应用挂载失败当成未处理异常，导致壳层渲染链被打断。后来改成子应用隔离失败，不影响主壳继续可用。
2. Q：兼容旧设备会不会拖慢新设备性能？
   A：会有少量成本，所以我们用差异化策略：现代包给新设备，legacy 只给老设备，控制影响面。
3. Q：如何定义“可以回滚”的发布标准？
   A：预设白屏率和崩溃率阈值，超过阈值自动触发回滚流程，5分钟内恢复上个稳定版本。

### 可背诵话术
这次事故让我意识到：稳定性不是监控上线就结束，而是“可观测 + 可降级 + 可回滚”的闭环。面试里我会重点讲我怎么在事故里做判断，并把一次救火变成长期治理。

## 场景4：安全、权限、隐私与医疗合规（病历数据保护）

### 1) 业务背景与目标
医疗系统涉及身份证号、联系电话、诊断信息、处方信息等敏感数据，且角色复杂（医生、护士、药师、运营、审计）。目标是通过院方安全审计，做到“最小权限、全链路可追溯、敏感信息最小暴露”。

### 2) 初始方案
初版是 JWT + 路由级 RBAC，页面上通过按钮显隐控制操作权限；前端缓存默认使用 `localStorage`，日志上报有时会携带完整请求体。

### 3) 踩坑表现
- 安全审计发现：护士角色通过构造 URL 可访问部分医生页面。
- 前端错误日志里偶发出现脱敏不完整的手机号。
- 某导出接口前端参数校验不足，存在越权风险提示。

### 4) 排查过程
- 与安全团队联合做权限穿透测试，列出可疑 URL 与字段。
- 审查前端埋点、错误日志、网关日志，确认敏感字段泄露路径。
- 回放权限链路：菜单权限通过，但字段权限和操作权限未统一校验。

### 5) 根因分析
技术根因：
- 只做了路由级 RBAC，缺少字段级与数据范围控制。
- 敏感信息脱敏在多个地方“手写”，没有统一策略。
- token 存放方式和本地缓存策略不够稳健。

流程根因：
- 0到1阶段安全评审介入偏晚。
- 权限模型没有和后端统一成“策略中心”，前后口径不一致。

### 6) 解决方案
短期止血：
- 立即下线高风险导出能力，敏感日志全量清洗。
- 所有关键接口改为后端强校验，前端显隐只做体验层。

长期治理：
- 权限模型升级为 RBAC + ABAC（角色 + 资源 + 数据范围）。
- 前端建立 `can(resource, action, scope)` 统一权限指令。
- 字段级脱敏组件化（手机号、证件号、地址），默认脱敏，按权限解密显示。
- token 改 HttpOnly Cookie，前端敏感缓存加密并设置最短生存期。
- 审计日志标准化：谁在何时查看了什么字段、执行了什么操作。

### 7) 架构取舍
备选方案A：纯 RBAC（角色控制）。
- 优点：实现快。
- 缺点：面对“同角色不同科室/病区/患者范围”时不够细。

备选方案B：RBAC + ABAC 混合策略。
- 优点：可表达医疗场景复杂权限，适配合规要求。
- 缺点：策略维护成本更高。

备选方案C：权限全部后端处理，前端不感知。
- 优点：安全边界清晰。
- 缺点：前端体验差，用户会频繁点到无权限操作。

最终决策：选 B，后端做强校验，前端做策略感知与体验优化。

### 8) 结果量化
- 高危权限漏洞：7 个 -> 0 个
- 敏感字段日志泄露事件：月均 3 起 -> 0 起
- 审计问题整改周期：4 周 -> 1.5 周
- 顺利通过院方年度安全与合规检查

### 9) 复盘沉淀
- 输出《医疗前端权限模型设计规范》与《敏感信息处理清单》。
- 安全评审前置到需求评审阶段，新增“合规检查项”。
- 将权限策略与字段脱敏纳入脚手架模板，减少项目间重复踩坑。

### 10) 面试表达版本
#### 30秒电梯版
我在医疗项目里做过一次权限与隐私体系重构。初版只做路由RBAC，审计时暴露了越权访问和日志脱敏不完整问题。短期我先下线高风险能力并清洗日志，长期把模型升级到 RBAC+ABAC、字段级脱敏组件化、后端强校验与审计闭环。最终高危漏洞清零，审计通过。

#### 3分钟完整版（STAR）
- S：系统进入院方审计阶段，发现权限与隐私治理存在明显短板。
- T：我要在不影响核心业务的情况下，完成权限体系升级并满足医疗合规要求。
- A：先做风险收敛：下线导出、日志清洗、后端强校验。再做体系建设：RBAC+ABAC、统一权限指令、字段脱敏组件、token 与缓存策略升级、审计日志标准化。
- R：高危漏洞清零，审计顺利通过，后续新功能接入权限模型的成本明显降低。

#### 面试官可能追问3个问题 + 最佳回答
1. Q：为什么前端还要做权限，不是后端就够了吗？
   A：安全边界必须在后端，但前端做权限感知能避免误操作和重复请求，提升体验并减轻无效流量。
2. Q：ABAC 会不会太复杂？
   A：复杂度确实高，所以我做了策略模板化和配置化，把常见场景沉淀成可复用规则，不靠页面手写。
3. Q：日志脱敏如何防止漏网？
   A：统一出口处理，任何上报前先过脱敏中间件，并加单测和审计脚本扫描高风险字段。

### 可背诵话术
这个案例我会强调“安全不是加个权限判断就完事”。医疗前端要把权限、脱敏、审计、缓存策略放在一个体系里。我做的是把零散 patch 变成可复用的合规能力。

## 场景5：构建部署、包体积与成本优化（多应用并行交付）

### 1) 业务背景与目标
平台扩展后形成 7 个前端子应用（问诊、病历、报告、药房、运营等），多团队并行开发导致构建与部署成本上升。目标是将主应用构建时间控制在 8 分钟以内，首屏包体积压到 5MB 以内，减少运维资源开销。

### 2) 初始方案
历史系统沿用 Webpack，新系统用 Vite，形成双构建链路；依赖管理不统一，多个子应用重复打入大体积 UI 与图表库。

### 3) 踩坑表现
- Jenkins 全量构建 18~22 分钟，发布窗口经常被占满。
- 主应用首屏静态资源 12MB+，院内网络高峰下载慢。
- 镜像体积不断变大，CI 机器和制品仓库存储成本攀升。

### 4) 排查过程
- 用 `rollup-plugin-visualizer` / `webpack-bundle-analyzer` 做包体画像。
- 分析 CI 阶段耗时，定位依赖安装与重复构建占大头。
- 统计子应用重复依赖，发现图标库和图表库存在整包引入。
- 对比 sourcemap 上传策略，发现非必要环境也在全量上传。

### 5) 根因分析
技术根因：
- 双构建体系缺乏统一规范，拆包策略不一致。
- 组件库与图标库未按需加载，重复依赖多。
- 缓存策略与构建缓存没打通，CI 每次“冷启动”。

流程根因：
- 没有统一的“包体积预算”与发布前检查门禁。
- 团队各自优化，缺少平台化视角。

### 6) 解决方案
短期止血：
- 先做按需引入和手动分包，砍掉最重的几个 chunk。
- 生产环境分级 sourcemap 策略，非核心环境不全量上传。

长期治理：
- 新应用统一迁到 Vite；旧 Webpack 应用保留过渡层，分阶段下线。
- 建立共享构建配置与依赖白名单，避免重复打包。
- CI 引入 pnpm 缓存 + 构建缓存 + 增量流水线。
- 资源预压缩（gzip/brotli）+ 静态资源长缓存策略。
- 包体积预算接入 MR 门禁，超阈值必须说明。

### 7) 架构取舍
备选方案A：全部继续 Webpack，做深度优化。
- 优点：迁移最小。
- 缺点：后续维护复杂，构建速度上限有限。

备选方案B：一次性全量迁移 Vite。
- 优点：长期收益高。
- 缺点：风险高，业务窗口不允许。

备选方案C：双引擎过渡（新用 Vite，旧逐步迁移）。
- 优点：风险可控，收益可逐步释放。
- 缺点：短期维护两套链路。

最终决策：选 C，配合统一规范和迁移里程碑，边交付边收敛。

### 8) 结果量化
- 主应用构建时长：19 分钟 -> 7 分钟
- 首屏静态资源：12.4MB -> 4.8MB
- CI 失败重跑率：18% -> 7%
- 制品与构建资源成本：季度下降约 31%

### 9) 复盘沉淀
- 输出《前端构建治理手册》与《包体积预算规则》。
- 建立“构建健康看板”：耗时、体积、失败率、成本四维可视化。
- 模板化生成 Vite 构建基线，减少新项目起步差异。

### 10) 面试表达版本
#### 30秒电梯版
我在医疗平台扩展期处理过构建与成本问题：7个子应用导致构建慢、包体积大、资源成本高。先通过按需引入和分包止血，再做双引擎过渡治理：新应用统一 Vite、旧应用分阶段迁移，配合CI缓存和体积门禁。最终构建从19分钟降到7分钟，首屏资源从12.4MB降到4.8MB。

#### 3分钟完整版（STAR）
- S：多团队并行后，构建链路和包体积失控，影响发布节奏与成本。
- T：我要在不打断业务开发的前提下，把构建效率和体积控制到可持续范围。
- A：先做体积画像和耗时拆解，短期通过按需加载、手动分包、sourcemap分级止血。长期采用双引擎过渡策略，统一 Vite 基线、建立缓存与增量流水线、接入包体积门禁。
- R：构建效率和成本都显著改善，且后续版本不再反复“涨包”。

#### 面试官可能追问3个问题 + 最佳回答
1. Q：为什么不一次性全迁 Vite？
   A：一次性迁移风险太高，会影响医疗业务连续交付。我们选分阶段迁移，保证每个迭代都可控可回滚。
2. Q：包体积治理里最有效的动作是什么？
   A：按需引入 + 重依赖拆分最直接；但真正长期有效的是预算门禁，不让问题反弹。
3. Q：如何量化“成本优化”不是拍脑袋？
   A：我用CI机器时长、制品仓库存储和发布失败重跑率做统一口径，季度复盘可追踪。

### 可背诵话术
这个案例我想体现的是架构取舍：不是追求“技术最先进”，而是选“业务可落地”的迁移路径。我做的是一边交付业务，一边把构建体系拉回健康区间。

## 场景6：工程效率提升（CI/CD、自动化测试、灰度与回滚、模板化）

### 1) 业务背景与目标
项目0到1阶段需求变化快，医院上线窗口固定。早期主要靠人工回归和夜间发布，目标是把发布节奏从“每月几次”提升到“每周稳定发布”，并把线上逃逸缺陷降到可控。

### 2) 初始方案
采用 GitFlow + 人工回归 + 手工发布脚本；测试以单元测试为主，缺少关键业务链路 E2E；没有统一灰度策略，回滚依赖人工操作。

### 3) 踩坑表现
- 一次处方剂量规则改动在生产漏测，导致紧急修复。
- 发布前回归时间长，业务方常被迫延期。
- 发生线上问题时回滚步骤分散，恢复慢。

### 4) 排查过程
- 统计近3个月事故与延期原因，发现 60% 与回归不足和发布流程相关。
- 拆解流水线耗时，识别“无效等待”和重复步骤。
- 复盘缺陷流入路径，定位到“接口联调通过但端到端链路未覆盖”。

### 5) 根因分析
技术根因：
- 自动化测试覆盖偏底层，关键业务链路缺口大。
- 发布缺少灰度与自动回滚，风险集中到全量上线时刻。
- 环境差异导致“测试通过，线上翻车”。

流程根因：
- 研发、测试、运维协作断点多，发布SOP不统一。
- 需求变更频繁但分支策略偏重，合并冲突与回归成本高。

### 6) 解决方案
短期止血：
- 发布冻结一天，补齐处方主链路 Cypress 冒烟。
- 整理一键回滚脚本，明确5分钟恢复流程。

长期治理：
- 分支策略改为 trunk-based + feature flag，缩短集成周期。
- CI 统一门禁：lint -> unit -> contract -> Cypress 冒烟 -> 构建。
- CD 增加灰度发布：按医院/科室逐步放量，指标异常自动回滚。
- 搭建医疗前端模板/低代码表单引擎，标准页面 60% 由模板快速生成。

### 7) 架构取舍
备选方案A：继续 GitFlow，强化人工回归。
- 优点：团队熟悉。
- 缺点：节奏慢，冲突和回归成本高。

备选方案B：trunk-based + feature flag + 自动化门禁。
- 优点：集成频率高，风险更早暴露，适合快速迭代。
- 缺点：对工程纪律要求高。

备选方案C：保守月度大版本发布。
- 优点：流程简单。
- 缺点：风险集中，问题一旦出现影响面大。

最终决策：选 B，用2个迭代完成团队迁移。

### 8) 结果量化
- 发布频率：月均 2 次 -> 月均 9 次
- 交付 Lead Time：9.2 天 -> 3.1 天
- 线上逃逸缺陷：季度下降约 58%
- 故障回滚平均耗时：27 分钟 -> 4 分钟
- 标准后台页面开发时长：平均 2.5 天 -> 1 天

### 9) 复盘沉淀
- 形成《发布SOP》《灰度与回滚SOP》《自动化测试分层策略》。
- 建立前端模板工程与低代码组件资产库。
- 推行“事故复盘不过夜”，问题必须落到规则或工具层。

### 10) 面试表达版本
#### 30秒电梯版
我在0到1阶段最大的效率坑是：靠人工回归和手工发布，节奏慢且容易漏测。后来我推动 trunk-based + feature flag，搭建 CI/CD 门禁和按医院灰度发布，并把回滚做成4分钟内可执行。结果发布频率从月均2次提升到9次，线上逃逸缺陷下降58%。

#### 3分钟完整版（STAR）
- S：医疗项目需求密集，原有发布方式导致延期和线上风险并存。
- T：我要同时提升交付速度和质量，避免“快了就不稳”。
- A：先补关键链路冒烟和回滚脚本止血；再系统升级工程流程：trunk-based、feature flag、CI门禁、灰度放量、自动回滚、模板化研发。
- R：发布节奏和稳定性同时改善，跨团队协作成本下降，标准需求交付更可预测。

#### 面试官可能追问3个问题 + 最佳回答
1. Q：医疗业务这么敏感，为什么敢提高发布频率？
   A：频率高不等于风险高，前提是小步灰度、自动门禁、可回滚。我们是把风险分散到可控小批次。
2. Q：Cypress 在你们场景里主要测什么？
   A：只测高价值主链路，比如问诊开单、处方提交、报告查看，不追求全量E2E，避免测试成本失控。
3. Q：低代码会不会牺牲可维护性？
   A：我们只模板化高重复场景，核心诊疗流程仍手写。模板是提效工具，不替代复杂业务建模。

### 可背诵话术
这个案例我会讲“效率和质量不是二选一”。我做的核心是把发布从人治变成机制：门禁、灰度、回滚、模板化。这样团队不是靠加班顶节奏，而是靠工程体系稳定交付。
